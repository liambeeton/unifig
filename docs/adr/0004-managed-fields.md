# Config models a few fields; the Controller has a hundred

A Resource in unifig.yaml describes a handful of fields — a network is a name, a VLAN and a subnet — while the Controller object behind it has around a hundred, and the Internal API stores whatever it is sent. So every write has to answer what happens to the fields the config never mentions, and the answer differs by verb: an **update** overwrites only the modelled fields and leaves the live Resource otherwise as it was, while a **create** starts from the Controller's own defaults for a new object of that type, because there is no live object to preserve and a bare struct would serialise as every feature switched off — a network with NAT and DHCP disabled is not a network.

_This paragraph originally ended its first sentence "stores whatever it is sent **rather than merging**", and said an update "puts the whole object back". Both were written of the create path and read across. They have since been measured, and what an endpoint does with a field the body leaves out turns out to be per endpoint: the v1 verbs merge and the v2 firewall-policy endpoint replaces, so "puts the whole object back" is literally true on one of them and the Controller's job on the other. The consequences below carry the measurements (ADR-0021, ADR-0023)._

"Mentions" is per field, not per Resource: a modelled field the file omits is unmanaged too, not a request to empty it. The schema gives no way to ask for a network with no VLAN or no subnet (`vlan` starts at 1, `subnet` must match a CIDR), so reading omission as removal would delete a setting the operator had no way to ask to delete. Removing a field's value is therefore a Controller-side operation, and `- name: X` alone is a valid entry meaning "match this Resource, manage nothing about it yet".

## Considered Options

- **Model every field** — rejected: the config file stops being human-owned, and the tool inherits the Internal API's undocumented surface as its public one.
- **Send only the modelled fields and let the Controller fill in the rest** — rejected: it does not. A create with three fields is stored with three fields, and the result is a network that cannot route or lease.
- **Write nothing unmodelled, ever** — rejected: it makes create unusable, and it does not even hold for update. A DHCP pool cannot stay in a subnet the network no longer has; the Controller rejects the whole update as an invalid range.

## Consequences

- Anything an operator sets in the Controller's UI survives an apply, so unifig can be adopted for one field of one Resource without taking ownership of the rest. This is what `--prune`'s absence means at field level.
- Create defaults are unifig's own policy and are set once. They are not re-asserted on update, so an operator's later edits win permanently.
- Where a modelled field's change strands an unmodelled one, unifig repairs the dependent field and says so in the plan. A plan that quietly did more than it printed would not be a plan, so any future case of this gets a note in the plan too, never a silent write.
- The same three rules are what each later resource area implements; the network engine (issue #3) is the worked example.
- "Puts the whole object back" is a claim about the request, and a struct is not the object. Where the live Resource is read through `go-unifi`, whatever that library does not model — and whatever `omitempty` elides at its zero value — is missing from the body, and what that costs depends on the endpoint. Both have now been measured, and they answer differently. The **v2** firewall-policy endpoint replaces, so the update deleted what the struct had dropped, and it is fixed there by merging into the JSON the Controller sent (ADR-0021). The **v1** verbs merge, so nothing was dropped — and the same struct wrote eighty-three fields onto a network that the Controller had never stored, which is the same defect facing the other way. They send only the fields the config states now, and the Controller does the merging (ADR-0023).
- "Stores whatever it is sent rather than merging" is true of a **create** and not of a v1 update, and the sentence above is the only place it was load-bearing. A network created with twelve fields is stored with those twelve and seven of the Controller's own, which is the whole reason `newNetwork` sets defaults at all; a network updated with two fields keeps the other ninety-eight (ADR-0023).
