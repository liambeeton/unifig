# Encrypted DNS is a singleton Setting, and its server list is one field

ADR-0010 left a question for whatever came next: a WAN slot is matched by `wan_networkgroup`, and "Encrypted DNS is a singleton rather than a slot, so it inherits the kind vocabulary but needs its own answer to *what identifies it*". The answer is that nothing does, and saying so out loud turned out to change three things.

**A singleton is matched by being the only one.** A Controller has exactly one Encrypted DNS setting — one `doh` key in `get/setting` — so there is no natural key, no slot, and nothing for a config file to name. The section is a mapping rather than a list, which makes two entries for one setting unsayable rather than an error to report, and `Change.Name` is empty. That last part reached the output: `~ encrypted-dns ""` would be printing an identity that does not exist, so the plan prints `~ encrypted-dns`, and `Change.Summary` grew a `subject()` beside it that the apply report and the failure message now share rather than each formatting a change their own way. The JSON keeps `"name": ""` rather than omitting the field, so a consumer reads an empty string where there is no name instead of having to know which kinds have one.

**The custom server list is one field, not a collection of Resources.** This is the first list-valued field unifig models, and the choice is between two rules that already exist in the codebase pulling in opposite directions. ADR-0004 says only the fields the config states are written; ADR-0006 says nothing is destroyed unless it was asked for. Read as Resources, the resolvers would need per-element create and prune semantics inside a Setting that cannot be created or pruned. Read as a field — which is what `custom_servers` is on the Controller — the existing rule covers it whole: no `servers:` key means unifig does not manage the list, and stating it states the list.

So a resolver dropping out of the file is removed on the next apply. That is the one place in unifig where deleting a line from the config changes something on the Controller, and it is not a prune: it is one field taking a new value, the same as a subnet. What makes it safe is that it is announced — the plan prints `servers: "AdGuard-DNS", "Quad9" -> "AdGuard-DNS"` before anything happens, and the operator approves that line like any other. `servers: []` says there should be none, and the nil-versus-empty distinction the loader already preserves for a whole section is what carries it.

Two things inside the list are deliberately not modelled. A resolver already on the Controller keeps every field unifig does not know about, its `enabled` toggle included, so an operator who switched one off in the UI does not have it switched back on by a stamp rotation; a resolver unifig is adding is enabled, for the same reason a WLAN passphrase implies WPA-PSK (ADR-0007). And the built-in provider list (`server_names`, used by `state: manual`) is left to the Controller's UI, so `state: manual` says which mode to be in and nothing about which providers.

Two consequences of "one field" only became visible once the code existed, and both are load-bearing enough to name:

- **`servers` is the one field in the config without `omitempty`.** A Controller with the setting and no resolvers has to export as `servers: []`. With `omitempty` the empty slice is dropped, and the file then says the opposite of what the Controller holds — *don't manage the list* rather than *the list is empty* — so the distinction this ADR rests on would be one export could not write.
- **A resolver's name is a natural key, so two live resolvers sharing one is refused.** The diff matches by name and so does the write, so guessing would have export produce a file its own validate rejects (breaking the brownfield promise) and an apply silently collapse the pair, deleting a resolver no plan line mentioned. It stops instead, the way two identically named networks do (ADR-0001), and says which name is ambiguous.

**A state unifig does not model is left out rather than copied through.** The schema's `state` is a closed set of the four the Controller offers today. ADR-0010 rejected enumerating the WAN slots precisely because "it would have let `export` write a file its own `validate` then rejected", and a firmware that adds a fifth state would do exactly that here. So `fromLiveEncryptedDNS` is guarded the way `fromLiveWANSlot` is: an unmodelled state comes back empty — unmanaged — and export says on stderr which state it could not describe. The enum stays, because the alternative is a free-text field that no editor can complete and no offline validate can check.

**Encrypted DNS is not a Risky change.** This was the closest call. A bad stamp breaks name resolution for the whole site, which an operator experiences as the internet being down, and ADR-0009's confirmation flow was right there to reuse. It is still the wrong line to draw. `CONTEXT.md` defines a Risky change as one that can sever internet or *management* connectivity, and the reason WAN qualifies is that the recovery may need physical access: get the uplink wrong and there may be no way back to the Controller at all. Encrypted DNS cannot do that. The uplink stays up, the Controller stays reachable on its LAN address, and the fix is one field in a UI the operator can still reach. Making it Risky would have meant an individual confirmation for every DNS change forever, which is how a confirmation prompt stops being read. What it does get is the position just before the WAN slot in the apply order, on the same reasoning one step down: there is no sense changing how a site resolves names before the changes that decide what there is to resolve.

## What the real UDR answered

The shape was read off a physical UniFi Dream Router running Network 10.5.67, read-only, and is what `e2e/testdata/udr/setting.json` holds:

```json
{ "key": "doh", "state": "custom", "server_names": [],
  "custom_servers": [ { "enabled": true, "server_name": "…", "sdns_stamp": "sdns://…" } ] }
```

**`sdns_stamp` reads back populated.** ADR-0007's finding holds for the third secret unifig models, so a stamp diffs like any other field and no write-only fallback is needed. Unlike ADR-0007's own subject, this one was confirmed on the physical router rather than on the dockerized Controller — `make record-udr` asks the question and prints the answer, which is how it will be asked again on the next firmware.

**And the whole read path was run against that router, not only recorded from it.** `unifig export` against the UDR wrote the section this Setting exists for — `state: custom`, one custom server, its stamp redacted to `${UNIFIG_DNS_ADGUARD_DNS_STAMP}` — which exercises `projectEncryptedDNS`, the state guard, the resolver-name-to-variable naming and the redaction notice through the real binary rather than through the stand-in. It is also the run that closed ADR-0007's outstanding UDR confirmation, since it redacted all three kinds of secret at once.

**One assumption is deferred, and it is about writing rather than reading.** `set/setting/doh` was never called against the real router: this program is read-only against a live site, and a bad stamp on the household's own resolver is not a test. What the replay stand-in assumes is that the Controller *replaces* the setting document with what was sent, the way it replaces a networkconf entry. It matters in exactly one case. The SDK's `custom_servers` field is `omitempty`, so `servers: []` reaches the Controller as a request with no `custom_servers` in it at all; a Controller that replaced the document reads that as "none", and one that merged would leave the resolvers where they are. If it merges, clearing the list is the one operation that silently does nothing — and the idempotence tests catch it the moment anyone runs the suite against a real Controller, because the next plan would not be empty.

## Considered Options

- **Model the resolvers as Resources inside the Setting, matched by name and merged** — rejected: it would mean a resolver could be added and updated through unifig but never removed, and it would put create-and-prune vocabulary inside a Setting that has neither. The removal would then be the one thing an operator had to go to the UI for, in the one place they had most reason to expect declarative behaviour.
- **Give the singleton a name anyway — `"encrypted-dns"` or `"default"` — so every change has one** — rejected: it is a name unifig invented, and the first person to match on it in a pipeline would be matching on nothing. An empty name is the honest answer and costs one branch in one function.
- **Make every Encrypted DNS change Risky** — rejected, as above. The distinction that survives is whether the recovery needs physical access.
- **Model `enabled` in the config** — rejected: the Controller's own toggle is a statement an operator made in the UI, and unifig preserves it for the same reason it preserves a VLAN tag on an uplink. A config that could disable a resolver it also declares is a config with two ways to say the same thing.
- **Record the whole `get/setting` response** — rejected: that response is the entire console's configuration — mail credentials, RADIUS secrets, remote access, guest portals — and unifig reads one key out of it. The recording keeps that one key, which is the same decision as emptying the WLANs (ADR-0011), taken where the stakes are higher.

## Consequences

- The next singleton Setting has an answer to inherit, and the plan already renders one. A Setting that turns out to be neither a slot nor a singleton would need a third answer, and the place to put it is `Change.Name`.
- `unifig export` now reads the settings collection on every run, and a Controller without the `doh` key gets a config with no section and a notice saying why — the same promise `WriteOmissions` makes about a WLAN it could not describe. Plan does not read it at all unless the file has the section (ADR-0006).
- The recording gained a fourth file and the scrub gained two shapes: a DNS stamp and the operator's name for their resolver. Both are counted rather than fixed, so a site with two resolvers records as two.
- `make record-udr` now answers three questions rather than two, and the third is this ADR's.
- A note in a plan can now be about the change rather than about one field (`annotateFirst`). Both of this Setting's notes follow from the state and the resolver list *together*, so hanging either off a single named field dropped it exactly when the other one moved — which is when an operator most needed it.
- "Only unifig's own fields are written" is bounded by what the SDK's generated type models, here and on every other write in this engine. A field of the `doh` document that `unifi.SettingDoh` has no place for is dropped when the response is decoded and cannot be handed back. Today's recording has no such field, so nothing would catch it if a firmware grew one.
